O que fazemos

Quatro frentes que aprendemos no curso e que juntamos em um mesmo sistema, da tela até a leitora de cartões.

Páginas institucionais, telas de login e dashboards que funcionam de 360 px a 1440 px sem rolagem horizontal. O JavaScript usa a Fetch API para atualizar tabelas e indicadores sem recarregar a página.

  • HTML5
  • CSS3
  • JavaScript
  • Fetch API

Back-end em PHP com PDO e consultas preparadas, senhas com password_hash, sessão com cookie HttpOnly e respostas JSON com códigos HTTP claros. A validação acontece no servidor, não só no navegador.

  • PHP
  • PDO
  • JSON
  • Sessões

Modelagem relacional em MySQL com chaves estrangeiras, restrições UNIQUE e desativação lógica para preservar o histórico. A estrutura vive em scripts SQL versionados, para qualquer integrante recriar o ambiente.

  • MySQL
  • schema.sql
  • seed.sql
  • Workbench

ESP32 com leitor RFID MFRC522 em 13,56 MHz, LEDs, buzzer e um relé de bancada que sempre começa desenergizado. O dispositivo só identifica: quem decide é o servidor.

  • ESP32
  • MFRC522
  • Wi-Fi
  • SPI

Machine Acesso a máquinas com RFID MVP em desenvolvimento P-01

O cartão identifica. A regra decide.

O LockMachine é o nosso TCC. Ele associa o cartão RFID do operador aos treinamentos registrados no banco e confere se continuam válidos antes de autorizar o uso da máquina. Liberada ou bloqueada, toda tentativa vira registro com o motivo.

  1. 1O operador aproxima o cartão da leitora.
  2. 2O servidor confere cadastro, máquina e validade das capacitações.
  3. 3O acesso é liberado ou bloqueado e fica no histórico.

Como trabalhamos

Desenvolvimento incremental com Scrum adaptado à escola. O Product Owner cuida do backlog e dos critérios de aceitação, o Scrum Master acompanha o andamento e cada integrante assume entregas pequenas e revisáveis.

  1. 1

    Problema e usuários

    Começamos pelo problema real: quem libera as máquinas, quem opera e o que cada perfil pode fazer no sistema.

  2. 2

    Requisitos mensuráveis

    Doze requisitos funcionais e sete não funcionais, cada um com um critério de aceitação que dá para verificar.

  3. 3

    Modelo de dados

    Sete tabelas relacionais, chaves estrangeiras e UNIQUE para e-mail, matrícula, código da máquina e UID.

  4. 4

    Back-end e rotas

    API em PHP sem framework, PDO com consultas preparadas, sessão nas rotas privadas e respostas JSON padronizadas.

  5. 5

    Integração

    Telas, API, banco e leitora RFID ligados pela rota de validação, uma entrega pequena por vez.

  6. 6

    Testes e evidências

    Casos de teste escritos antes da execução. Nada vira “aprovado” sem uma evidência datada.
